A* Search

Unit 4 AOS2 · Additional topic 1 of 4 — shortest paths with a sense of direction

VCE Algorithmics (HESS) · Northcote High School

Why not just use Dijkstra?

  • Dijkstra finalises nodes in order of distance from the start. It has no idea where the goal is, so it grows outwards evenly in every direction.
  • For one start and one goal, most of that work is wasted: it carefully finds shortest paths to places you are walking away from.
  • Often we do know something about where the goal is — a map gives straight-line distance, a maze photo shows where the centre is.
The idea

A* is Dijkstra with an estimate of the distance still to go added to each node's priority. Nodes that are close to the start and look close to the goal get expanded first.

Where it lives in the course

A* is a heuristic-guided search, but — unlike hill climbing — with the right heuristic it still guarantees the shortest path. Hold on to that contrast.

The priority: \(f(n) = g(n) + h(n)\)

Three quantities per node

\(g(n)\) — the cost of the best path found so far from the start to \(n\). Known exactly, as in Dijkstra.

\(h(n)\) — a heuristic estimate of the cost from \(n\) to the goal. Guessed, never computed by search.

\(f(n) = g(n) + h(n)\) — the estimated cost of the cheapest complete path through \(n\). The priority queue is ordered on this.

Choice of \(h\)What A* becomes
\(h(n) = 0\) for every nodeexactly Dijkstra's algorithm
\(h\) admissible (never overestimates)optimal, and usually expands far fewer nodes
\(h(n)\) = the true remaining costwalks straight down the optimal path
\(h\) sometimes overestimatesfaster still, but can return a non-optimal path

A* in pseudocode

Algorithm AStar(G, start, goal, h):    g[start] ← 0;  g[v] ← ∞ for every other v    parent[start] ← null    PQ ← priority queue containing start with priority h(start)    While PQ is not empty Do        u ← PQ.removeMin()                 // smallest f = g + h        If u = goal Do            Return path rebuilt from parent[]        Foreach neighbour v of u Do            If g[u] + w(u, v) < g[v] Do   // relax, as in Dijkstra                g[v] ← g[u] + w(u, v)                parent[v] ← u                PQ.insertOrUpdate(v, g[v] + h(v))    Return no path
Spot the difference

Delete + h(v) on line 13 and h(start) on line 4, and this is Dijkstra line for line. The other change: A* stops when the goal is removed from the queue, not when the queue empties.

A worked instance

  • Find the shortest path from S to G. Edge weights in black.
  • h (orange) is the straight-line distance to G, rounded down.
  • No road can be shorter than a straight line, so \(h\) never overestimates.
Before we trace it

W is only 3 from S — the cheapest first step. Will A* ever expand W? Will Dijkstra?

Tracing A* — always expand the smallest \(f\)

  1. 1 Expand S (\(f = 0 + 9 = 9\)). Add A: \(4 + 6 = 10\), B: \(7 + 6 = 13\), W: \(3 + 12 = 15\).
  2. 2 Expand A (\(f = 10\)). Add C: \(8 + 3 = 11\), X: \(10 + 11 = 21\).  Queue: C 11, B 13, W 15, X 21.
  3. 3 Expand C (\(f = 11\)). Add G: \(12 + 0 = 12\). B via C would cost \(13 > 7\), so no update.  Queue: G 12, B 13, W 15, X 21.
  4. 4 Remove G (\(f = 12\)) — it is the goal, so stop.
  5. ✓ Path S → A → C → G, cost 12. Four nodes expanded; B, W and X never were.
Why it is safe to stop at G

Every other entry in the queue has \(f \ge 13\). Since \(h\) never overestimates, any path through them costs at least 13 — so nothing left can beat 12.

Same graph, same answer, half the work

A* — expands S, A, C, G

Dijkstra — expands all eight nodes

  • Dijkstra expands W first — it really is the closest node to S — and then X, B and D, all of which lead away from G.
  • Both return S → A → C → G at cost 12. The heuristic changed how much was searched, not the answer.

Admissible heuristics

Admissible

A heuristic \(h\) is admissible if it never overestimates: \(h(n) \le\) the true cheapest cost from \(n\) to the goal, for every node \(n\).

The guarantee

With an admissible heuristic, A* is guaranteed to return a shortest path. An optimistic estimate can only make a node look better than it is, so the true best path is never left sitting in the queue behind a worse one.

SettingA standard admissible \(h\)
Road map, any directionstraight-line (Euclidean) distance to the goal
Grid, moves up/down/left/right onlyManhattan distance \(|x_1 - x_2| + |y_1 - y_2|\)
Anything at all\(h = 0\) — admissible, but gives no guidance (Dijkstra)

When the heuristic overestimates

Take three nodes: S–G costs 10 directly; S–A costs 1 and A–G costs 1. The true shortest path is S → A → G, cost 2.

Now suppose a bad heuristic claims \(h(A) = 20\).

  1. 1 Expand S. Queue: G with \(f = 10 + 0 = 10\); A with \(f = 1 + 20 = 21\).
  2. 2 Remove G (smallest \(f\)) — it is the goal, so A* stops.
  3. ✗ Returns S → G at cost 10. The optimum was 2.
What went wrong

\(h(A) = 20\) but the real cost from A is 1. The overestimate buried the best path behind the goal, and A* stopped before ever looking at it.

A deliberate trade

Inflating \(h\) on purpose (e.g. \(3 \times\) straight-line) is a real technique: fewer expansions, faster answers, no optimality guarantee. That version is a heuristic in the T10 sense.

Complexity and where A* fits

  • Worst case: no better than Dijkstra, \(O((V + E)\log V)\) with a binary-heap priority queue — with \(h = 0\) it is Dijkstra.
  • In practice: a good admissible heuristic prunes most of the graph, which is why A* is the standard for route-finding, game path-finding and puzzles.
  • Memory is often the real limit: every generated node sits in the queue.

Not a heuristic algorithm

With an admissible \(h\), A* is exact. The heuristic buys speed without giving up the guarantee — the same point T10 made about Dijkstra being greedy but not a heuristic.

Exam focus

The maze-solving program

Adapted from VCAA Algorithmics (HESS) Written Examination 2023, Section A Q8

A program takes a satellite photo of a maze, uses image recognition to find the walls, entrance and centre, and returns a path from the entrance to the centre. — which is likely to be most efficient?

Abreadth-first search
Bdepth-first search
CDijkstra's algorithm
Dthe A* algorithm
Before you look

What does the photo give the program that a plain list of corridors would not?

Working it through

  1. 1 The photo tells us where the centre is. Every corridor junction has coordinates, so the distance to the centre can be estimated — a heuristic is available for free.
  2. 2 BFS and Dijkstra ignore the goal's position. They are correct, but expand outward in every direction until they happen to reach the centre.
  3. 3 DFS finds a path, with no guarantee it is short, and can wander down long dead ends first.
  4. 4 A* uses the estimate (e.g. Manhattan distance to the centre, which never overestimates in a grid maze) to expand promising junctions first, while still returning a shortest path.
  5. ✓ Answer: D.
The trigger

Whenever a question mentions coordinates, a map, or a known goal location, ask whether it is quietly offering you a heuristic — and therefore A*.

A short-answer version

Question (3 marks)

A navigation app uses A* on a road network with straight-line distance to the destination as \(h\). (a) Explain why this heuristic is admissible. (b) A developer proposes using three times the straight-line distance to speed the search up. Explain the consequence.

Answer

(a) No road between two points is shorter than the straight line between them, so the straight-line distance is never more than the true remaining road distance — it never overestimates. [1]

(b) Tripling it can overestimate the remaining cost, so it is no longer admissible. [1] The search will usually expand fewer nodes and finish faster, but A* is no longer guaranteed to return the shortest route. [1]

Where the marks are

"Never overestimates" is the definition — say it in those words. For (b), one mark for losing admissibility, one for naming both sides of the trade: faster, but optimality not guaranteed.

Check yourself

State what \(g(n)\), \(h(n)\) and \(f(n)\) represent in A*.

\(g(n)\): cost of the best known path from the start to \(n\). \(h(n)\): heuristic estimate of the cost from \(n\) to the goal. \(f(n) = g(n) + h(n)\): estimated total cost of a path through \(n\) — the priority-queue key.

What does A* become when \(h(n) = 0\) for every node? Is it still optimal?

It becomes Dijkstra's algorithm (stopping once the goal is removed). Yes — \(h = 0\) never overestimates, so it is admissible and the path is still shortest; it just gets no guidance towards the goal.

On a grid where diagonal moves are allowed at cost 1, is Manhattan distance admissible?

No. One diagonal step moves 1 across and 1 up for cost 1, but Manhattan distance counts it as 2 — an overestimate. Use \(\max(|\Delta x|, |\Delta y|)\) instead.

Give one situation where A* has no advantage over Dijkstra.

When you need shortest paths from one source to every node (A* targets a single goal), or when no useful estimate of the remaining distance exists, so \(h\) is effectively 0.

One sentence to remember

A* orders the search by \(g + h\) — cost so far plus an estimate of cost to go — and as long as that estimate never overestimates, it finds the shortest path while searching far less than Dijkstra.
