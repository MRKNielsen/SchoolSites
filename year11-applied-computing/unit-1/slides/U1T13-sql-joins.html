Why this lesson exists

We split the data into three tables so each fact is stored once. A join is how you put it back together for one question — without ever re-creating the redundancy.

Starting point

The question spans two tables

“What was the hottest day at Cape Otway?”

The temperature is in observation. The name “Cape Otway” is in station. Neither table can answer it alone.

What a join does

Matches each row of one table to the related row in another, using the foreign key, and hands you the combination as if it were one table.

Key knowledge

The shape of a join

SELECT s.station_name, o.obs_date, o.max_temp_c
FROM observation o
JOIN station s ON s.station_id = o.station_id
WHERE s.station_name = 'Cape Otway Lighthouse'
ORDER BY o.max_temp_c DESC
LIMIT 1;

PartDoes
FROM observation oStart here. o is an alias — a short name for the table
JOIN station sAlso read this table, aliased s
ON s.station_id = o.station_idMatch rows where the keys agree
s.station_namePrefix tells SQL — and the reader — which table a column came from

The part that bites

Unmatched rows disappear silently

An INNER JOIN keeps only rows that matched. Our raw extract has six observations for station 99999, which exists in no station table.

Join them and those six rows vanish. No error. No warning. Your totals are quietly six short.

How to catch it

Count before and after. If the join lost rows, find out why before going further.

LEFT JOIN keeps the unmatched rows with NULLs in the missing columns — which is how you find orphans rather than losing them.

Key knowledge

Each join adds one table

SELECT r.region_name, s.station_name, o.obs_date, o.rainfall_mm
FROM observation o
JOIN station s ON s.station_id = o.station_id
JOIN region r ON r.region_id = s.region_id
WHERE o.rainfall_mm > 40
ORDER BY o.rainfall_mm DESC;

The chain follows the relationships: observation → station → region. You cannot jump straight from observation to region, because there is no key between them.

Worked example

I do “Which region had the wettest single day?”

  1. 1 Where does rainfall live? observation. Start there.
  2. 2 Where does the region name live? region. But there is no key joining them directly.
  3. 3 The path is observation → station → region. Two joins.
  4. 4 Sort by rainfall descending and take the top row.
  5. ✓ SELECT r.region_name, o.obs_date, o.rainfall_mm
    FROM observation o
    JOIN station s ON s.station_id = o.station_id
    JOIN region r ON r.region_id = s.region_id
    ORDER BY o.rainfall_mm DESC
    LIMIT 1;
Follow the keys

You can only join where a foreign key exists. Draw the three tables and the arrows between them, and the path is obvious.

Together

We do What is wrong with each?

1. FROM observation JOIN station ON station_id = station_id

Ambiguous — both tables have station_id. Prefix them

2. FROM observation o JOIN region r ON r.region_id = o.region_id

observation has no region_id. Join through station

3. The join runs, but returns 2184 rows instead of 2190

Six orphan rows were dropped. Station 99999
