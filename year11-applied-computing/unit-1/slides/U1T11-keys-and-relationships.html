One of these words will cost you marks

Referential integrity. It means the relationships actually hold — and in SQLite it is switched off until you switch it on.

Key knowledge

The field that identifies the record

A primary key uniquely identifies one record. No two rows share it, and it is never empty.

In our data:

  • region.region_id
  • station.station_id — the real Bureau station number
  • observation.obs_id
Natural or surrogate?

station_id is a natural key — it already meant something before we had a database.

obs_id is a surrogate key — invented, meaningless, and reliable precisely because it means nothing.

Key knowledge

The field that points at another table

A foreign key holds the primary key of a different table. That is the whole mechanism of a relational database.

observation.station_id is a foreign key pointing at station.station_id.

station.region_id points at region.region_id.

One to many

One region has many stations. One station has many observations.

The foreign key always lives on the many side. A station does not list its 365 observations; each observation names its station.

The one to remember

SQLite will not enforce this unless you ask

Declaring a foreign key is a statement of intent. Enforcing it is a separate switch, and it is off by default.

With it off, this works:

INSERT INTO observation VALUES (9999, 404, '2025-06-01', 8.0, 15.0, 0.0, 70);

Station 404 does not exist. The row goes in anyway, and you now have an orphan record.

Switch it on, every session

PRAGMA foreign_keys = ON;

Put it at the top of every script. With it on, the same insert fails with FOREIGN KEY constraint failed — which is what you want.

Worked example

I do What identifies an observation?

  1. 1 Could obs_date be the key? No — six stations share every date.
  2. 2 Could station_id? No — each station has 365 rows.
  3. 3 Could station_id and obs_date together? Yes. One station records one observation per day.
  4. ✓ That pair is a composite key. Our table uses a surrogate obs_id instead, and enforces the pair as a UNIQUE constraint.
Why both

The surrogate key makes joins simple. The unique constraint on the pair still stops the same station recording two observations for one day — which is what actually goes wrong.

Together

We do Would this work as a primary key?

1. Student surname

No — surnames repeat, and can change

2. Student ID issued by the school

Yes — unique, never empty, never reused

3. Email address

Usually — but it changes, and every row referencing it must change too

The hidden cost in number 3

A key that can change has to be updated everywhere it is referenced. That is why surrogate keys exist.
