Starting point

Most software fails before anyone writes code

Ask someone to build you “an app for the canteen” and you will get something. It probably will not be what you wanted.

Not because they cannot code. Because nobody agreed what the thing had to do, who it was for, or how you would know it was finished.

Key idea

A methodology is an agreed order of work. It does not make you clever. It stops you building the wrong thing quickly.

Part 1

The four stages

Analysis → Design → Development → Evaluation

Overview

Analysis, design, development, evaluation

StageThe question it answersWhat it produces
AnalysisWhat is required to solve this problem?Requirements, constraints, scope
DesignHow will it function and appear?Designs, evaluation criteria
DevelopmentDoes it actually work?A working solution, tested
EvaluationDid it solve the problem?A judgement against the criteria

The stages can run once, straight through, or repeat on every cycle of an agile process. The order within a cycle does not change.

Stage 1 · Analysis

Determining what is required

Analysis

Acquiring and analysing data, then identifying the solution requirements, constraints and scope.

You are not deciding how to build anything yet. You are finding out what “done” means.

In Unit 1

Mostly done for you. Requirements and designs are teacher-provided, and your job is to interpret them.

You run analysis yourself in Unit 2, on a problem you choose.

Analysis · vocabulary

Functional and non-functional requirements

TermSay it like thisExample
FunctionalWhat the solution must do“Calculates the mean maximum temperature for each station”
Non-functionalWhat it must be like“Readable by a Year 7 student”, “loads in under two seconds”
Test for telling them apart

Could you write a pass/fail test for it by running the solution once? That is usually functional. Is it a quality the whole thing has — usable, reliable, portable, robust, maintainable? That is non-functional.

Analysis · vocabulary

Constraints and scope

Constraints

Conditions or limitations you must work within. Economic, technical, social, legal, usability.

“We only have the school laptops, and it has to be finished by week 8.”

Scope

The boundaries of the solution — what it will and will not address.

“It shows the data. It does not let you edit it.”

Scope is the most useful sentence you will ever write on a project, because it is the one you point at when someone asks for something extra in week 7.

Stage 2 · Design

Determining how it will function and appear

Design

Designing the functionality, appearance and user interface, and developing the evaluation criteria that decide whether the finished thing is any good.

Criteria come first

You write the evaluation criteria in design, before anything is built, and use the same criteria in evaluation at the end.

Writing them afterwards is marking your own homework.

Stage 3 · Development

Turning designs into a working solution

Four activities, and you will be assessed on all of them:

  1. 1 Manipulation — building it, using the functions and features of your tools
  2. 2 Validation — checking that the data going in is reasonable
  3. 3 Testing — checking that what comes out is correct
  4. 4 Documentation — explaining it, so somebody else can maintain it

Stage 4 · Evaluation

Did it solve the problem?

Evaluation

Judging the solution against the evaluation criteria written back in design, and saying how well it met the requirements.

Discuss

Evaluation happens after the solution has been used for a while. Why can you not evaluate it properly on the day you finish it?
